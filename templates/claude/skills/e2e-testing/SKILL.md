# /e2e-testing — Сквозное тестирование

Проверяешь работающее приложение целиком: поведение и вёрстку в разных viewport'ах/браузерах, граничные и нештатные
сценарии. Не чинишь баги — только находишь и репортишь (фикс — отдельно, через скилл `bug` или руками).

## Как использовать

```
/e2e-testing                        # полный прогон по всем флоу и viewport'ам
/e2e-testing только лобби и кошелёк # прогон конкретных флоу
/e2e-testing mobile                 # только мобильные viewport'ы
```

## Инструмент

Playwright MCP (`mcp__plugin_playwright_playwright__*`). Требует запущенного dev-сервера (`pnpm run dev`) — подними,
если не поднят, и проверь актуальный порт в выводе Vite.

**Ограничение движка**: этот MCP-сервер по умолчанию поднимает только Chromium. Настоящего WebKit (Safari) и Firefox
через него не получить. Поэтому:

- автоматизированный прогон = Chromium desktop + Chromium с разными viewport (эмуляция mobile/tablet через
  `browser_resize`, это ловит layout-баги, но НЕ движковые различия рендеринга);
- Safari (macOS/iOS) и Telegram in-app WebView (Android/iOS) — движки с историей расхождений на этом проекте (PWA
  install prompt, `100vh`/safe-area, backdrop-filter, position: sticky) — в отчёт всегда добавляй секцию
  "Требует ручной проверки" с чек-листом конкретных мест, которые стоит перепроверить руками в реальном Safari и в
  Telegram, а не молчи об этом ограничении.

## Рекомендация по контексту

Скриншоты и network/console-логи Playwright быстро забивают контекст. Если раннер вызван из интерактивной сессии (не как
fresh-агент сам по себе) — запусти прогон через `Agent(subagent_type: general-purpose)` с доступом к Playwright MCP,
отдай ему этот файл-скилл целиком как инструкцию в промпте, попроси вернуть только готовый баг-репорт (без сырых
скриншотов/логов в ответе, только пути к сохранённым файлам). В основную сессию должен попасть только финальный отчёт.

## Матрица viewport'ов

Продукт — SPA в вебе (installable PWA) и Telegram Mini App, мобильный трафик приоритетнее десктопного.

| Профиль           | Разрешение | Зачем                                      |
|-------------------|------------|--------------------------------------------|
| Mobile (основной) | 390×844    | iPhone 12/13/14, эталон для TMA/PWA        |
| Mobile (Android)  | 360×800    | самый частый Android-размер                |
| Small mobile      | 320×568    | нижняя граница — iPhone SE, старые Android |
| Tablet            | 768×1024   | iPad portrait                              |
| Desktop           | 1440×900   | веб-версия в браузере                      |

На каждом profile: `browser_resize` → `browser_navigate` → `browser_snapshot`. Проверяй горизонтальный скролл (его быть
не должно), обрезанный/наслаивающийся текст, недоступные из-за safe-area кнопки, состояние
`шортлейаута` (см. `AppLayout.tsx` — `css.shortLayout` зависит от того, страница `/game` или нет).

## Шаг 0 — Разведка: собери список флоу сам

Список флоу нигде не хардкодь и не бери из памяти прошлого прогона — домены и фичи меняются, скилл должен работать и
через полгода новых фич без правки этого файла. Собери актуальную карту приложения прямо перед прогоном:

1. **Роуты**: прочитай все `src/shared/routes/*.routes.ts` (это классы вида `<Domain>Routes` с путями) и
   `src/app/config/routes.ts` (маппинг путей на компоненты-страницы) — это полный список экранов приложения на момент
   прогона.
2. **Домены и фичи**: пройдись по `src/domains/*/pages/*` (страницы = кандидаты на отдельный флоу верхнего уровня) и
   `src/domains/*/features/*` (действия/формы внутри страниц — модалки, сабмиты, под-флоу без отдельного роута). Одна
   директория в `features/` без собственного роута = не отдельный флоу, а edge-кейс/шаг внутри флоу той страницы, где
   она используется (найди по импортам).
3. **README фич**: если у `features/<x>/` есть `README.md` — прочитай, там описаны назначение, ключевые файлы и нюансы
   фичи (по правилам CLAUDE.md проекта эти README обязаны быть актуальны). Бери оттуда реальные бизнес- правила и
   известные подводные камни для edge-кейсов, а не додумывай.
4. **Сводный индекс**: если есть `docs/domains-index.md` — глянь как отправную точку (список фич по доменам), но не как
   единственный источник: он может отставать от кода, свежий обход `pages/`/`features/` — источник правды.
5. **Реальные ограничения форм**: для каждой фичи с формой найди `validations.ts`/`schema.ts` рядом с ней и возьми
   оттуда фактические min/max/regex — граничные edge-кейсы стройте по факту в коде, не на глаз.
6. **Приоритизация**: если пользователь не ограничил скоуп явно, определи бизнес-критичные флоу эвристикой —
   домены/фичи, задевающие деньги, баланс, авторизацию или состояние членства (grep по домену/названиям фич на
   `wallet`, `balance`, `payment`, `withdraw`, `deposit`, `auth`, `login`, `signup`, `join`, `membership` и аналоги) —
   тестируй их первыми и полнее (весь список edge-кейсов ниже). Остальные флоу — happy path + базовые edge-кейсы
   (валидация, пустое состояние, refresh).
7. Из этой разведки собери пронумерованный список флоу с путём и исходной директорией — он идёт в отчёт как раздел
   "Охват" (см. итоговую структуру ниже), чтобы было видно, что именно было найдено и прогнано.

Если пользователь просит "только X" (по названию домена/фичи/раздела) — ограничься найденными в разведке флоу,
подпадающими под это ограничение, но всё равно прогоняй edge-кейсы для них полностью.

## Edge-кейсы (обязательные, не только happy path)

Для каждого флоу, где применимо:

- **Валидация форм**: пустое поле, граничная длина (мин/макс символов — сверяйся с `*/validations.ts`, не с ощущениями),
  запрещённые символы, вставка через paste, автозаполнение браузера.
- **Двойной сабмит**: быстрый двойной клик/тап по кнопке отправки — не должно уйти два запроса или сломать UI.
- **Сеть**: имитация 401 (истёкшая сессия) — куда редиректит; медленная сеть/оффлайн на середине флоу (
  `browser_network_request`/эмуляция через DevTools недоступна напрямую в MCP — как минимум проверь, что при зависшем
  запросе есть loading-индикатор и нет двойных сабмитов).
- **Навигация**: `browser_navigate_back` посреди флоу (например, после сабмита формы), обновление страницы (F5) в
  середине флоу — куда попадает пользователь, не теряется ли состояние авторизации.
- **Прямые ссылки**: заход на любой защищённый роут из карты шага 0 без авторизации и с истёкшим токеном — должен
  случиться редирект на страницу входа, а не белый/чёрный экран (гейты ищи в `layout/`).
- **Редирект-цепочки**: везде, где есть условная логика "куда отправить пользователя" (auth-гейты в лэйаутах, успешный
  сабмит формы, membership/статусные проверки) — редирект должен быть один прыжок в верное место, а не промежуточный
  экран, который тут же сменяется следующим. Найди такие гейты грепом по `window.open`/
  `window.location`/навигационным `useEffect` в `layout/` и точках входа фич, прогони с состоянием "на полпути"
  (например, только что созданная сущность без вложенных данных) и смотри на URL-переходы через
  `network_requests`, а не только на финальный экран.
- **Пустые состояния**: для каждого экрана со списком/коллекцией — пустая выдача, а также "свежая" сущность без
  связанных данных (только что созданный пользователь/объект без дочерних записей).
- **Длинный текст**: любое пользовательское текстовое поле на границе максимальной длины (сверься с реальным
  `validations.ts` фичи) — не должен ломать вёрстку карточек/списков/шапки.
- **i18n**: переключение en↔zh не ломает layout (китайский текст обычно короче/выше по строке — проверь переполнение).

## Алгоритм прогона

1. Убедись, что dev-сервер запущен и есть актуальный `develop` (если это часть более широкой сессии — не делай
   `git pull`/переключение веток без явной необходимости, это тестовый прогон, а не разработка).
2. Проведи разведку по шагу 0 — собери актуальный список флоу с приоритизацией.
3. Для каждого найденного флоу (с учётом ограничения пользователя, если оно было):
    - на каждом viewport из матрицы: `browser_resize` → `browser_navigate` → `browser_snapshot`;
    - выполни happy path руками через `browser_click`/`browser_type`/`browser_fill_form`;
    - после каждого значимого шага (сабмит формы, редирект, открытие модалки) — `browser_console_messages` (ищи
      `error`/`warning` уровня, необработанные promise rejections) и `browser_network_requests` (ищи 4xx/5xx, зависшие
      pending-запросы);
    - прогони релевантные edge-кейсы из списка выше;
    - при найденной аномалии — `browser_take_screenshot` немедленно, до того как состояние изменится дальше.
4. Не чини найденное по ходу — фиксируй в баг-лист и продолжай прогон. Исключение — если баг блокирует продолжение
   прогона данного флоу (например, форма вообще не сабмитится) — тогда отметь как **blocker** и иди к следующему флоу.
5. В конце — собери отчёт (шаблон ниже), сохрани в `docs/qa/e2e-<YYYY-MM-DD>.md` (создай `docs/qa/`, если нет) и выведи
   краткую сводку пользователю в чат: сколько флоу прогнано, сколько багов по severity, самое критичное — текстом, не
   только в файле.

## Формат бага в отчёте

```md
### [BUG-N] <короткое название>

- **Severity**: blocker / high / medium / low
- **Флоу**: <например, "Регистрация">
- **Viewport/браузер**: <например, "390×844, Chromium">
- **Шаги**:
    1. ...
    2. ...
- **Ожидалось**: ...
- **Получено**: ...
- **Консоль/network**: <ошибка, если была, иначе "—">
- **Скриншот**: <путь к сохранённому файлу>
- **Предположительное место в коде**: <файл:строка, если удалось определить по маршруту/компоненту>
```

Severity:

- **blocker** — флоу нельзя пройти вообще (крашится, белый экран, бесконечный редирект-луп)
- **high** — флоу проходим, но с потерей данных/некорректным состоянием (двойное списание, неверный редирект, доступ без
  авторизации)
- **medium** — заметный визуальный/UX баг, не блокирует задачу (обрезанный текст, наслоение, некорректный лоадинг)
- **low** — косметика, edge-кейс с низкой вероятностью

## Итоговая структура отчёта

```md
# E2E-прогон <дата>

## Сводка

Флоу: N/N пройдено. Багов: blocker: X, high: X, medium: X, low: X.

## Охват (результат разведки шага 0)

<список найденных флоу: путь, домен/фича-источник, приоритет (критичный/обычный) — чтобы было видно, что именно попало в
прогон и на основании чего>

## Требует ручной проверки (движки вне Chromium)

- <конкретный пункт> — почему автоматика не покрывает

## Найденные баги

<по одному блоку на баг из шаблона выше, blocker/high первыми>

## Что прогнано, багов не найдено

<список флоу × viewport, чтобы было видно охват, а не только проблемы>
```

## Чего не делать

- Не чинить баги в рамках этого прогона — только фиксировать. Фикс отдельным шагом/скиллом `bug`, по запросу
  пользователя.
- Не выдумывать флоу/роуты и не полагаться на список из прошлого прогона — каждый раз заново собирать карту по шагу 0,
  домены и фичи меняются.
- Не ограничиваться happy path — отчёт без edge-кейсов не считается полным прогоном.
- Не молчать про WebKit/Firefox/Telegram WebView — явно писать, что это не покрыто автоматикой.
