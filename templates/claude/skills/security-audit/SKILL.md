# Аудит безопасности

Повторяемый проход по репозиторию для поиска 50 классов уязвимостей, которые чаще всего встречаются в быстро собранных и
AI-сгенерированных приложениях. Цель — конкретный приоритизированный отчёт, по которому разработчик может действовать:
каждая находка привязана к файлу и строке, имеет severity и фикс.

## Базовые правила

- **Только defensive.** Скилл находит и объясняет слабые места, чтобы их починили. Не пиши эксплойты и не превращай
  находки в оружие — короткий proof-of-concept, чтобы *продемонстрировать* баг, допустим, рабочий атакующий инструмент —
  нет.
- **Указывай локацию.** Каждая находка называет файл и строку (или роут/ключ конфига). «В приложении есть XSS»
  бесполезно; `src/pages/Profile.tsx:42
  — dangerouslySetInnerHTML на несанитизированном bio` — по этому можно действовать.
- **Проверяй перед тем, как флагать.** Grep даёт кандидатов, а не вердикты. Прочитай окружающий код, прежде чем называть
  что-то уязвимостью, а то, что не удалось подтвердить до конца, помечай `NEEDS REVIEW`, а не как подтверждённую
  находку.
- **Отсутствие — это тоже находка.** Многие пункты (нет rate-limit, нет audit-логов, нет защиты от CSRF) — про то, чего
  *не хватает*. Если поискал и ничего не нашёл — это репортабельный пробел, а не повод молча пропустить.

## Процесс

Иди по фазам по порядку. Не бросайся сразу грепать — инвентаризация определяет, какие проверки вообще применимы.

### 1. Инвентаризация репозитория

Прежде чем аудитить, разберись, что именно аудитишь:

- Определи стек: `package.json` / `requirements.txt` / `go.mod` / `Gemfile`, фреймворк (Next.js, NestJS, Express,
  Django, Rails, Supabase, Firebase…) и где проходят границы доверия (клиент vs сервер vs БД vs third-party).
- Составь карту точек входа: HTTP-роуты/контроллеры, serverless-функции, обработчики вебхуков, эндпоинты загрузки файлов
  и любые вызовы AI/LLM.
- Найди конфиги: `.env*`, облачная конфигурация (`firebase.json`,
  `firestore.rules`, Supabase RLS, S3/bucket policy, `vercel.json`,
  `next.config.js`), CI.
- Зафиксируй модель аутентификации: сессии vs JWT, кто выдаёт токены, как защищены роуты, есть ли мультитенантность.

### 2. Прогон по чек-листу

Пройди **`references/checklist.md`** категория за категорией (A–J). Там все 50 проверок с конкретными командами поиска и
описанием того, как выглядит реальная находка. Пропускай проверку, только если стек делает её невозможной (например, нет
SQL → SQL injection N/A), и укажи это в отчёте явно, а не выбрасывай молча.

Сначала автоматический поиск (ripgrep, `npm audit`, `git log`), затем читай кандидатов руками. Категории A (секреты), C
(авторизация) и F (оплата/вебхуки) — где скапливаются баги с наибольшим импактом в таких приложениях; на них трать
больше всего времени.

### 3. Триаж по severity

Присвой каждой находке severity, чтобы разработчик понимал, что чинить первым:

| Severity     | Что значит                                                    | Примеры                                                                                                   |
|--------------|---------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| **Critical** | Прямой путь к полной компрометации или массовой утечке данных | Живые креды БД в репо, world-writable правила Firestore, обход аутентификации, IDOR по всем пользователям |
| **High**     | Серьёзный пролом при небольшом предусловии                    | SQLi за логином, JWT подписан угадываемым секретом, проверка оплаты только на фронте                      |
| **Medium**   | Реальная слабость с ограниченным радиусом или требует цепочки | Нет rate-limit, подробные stack trace, permissive CORS, устаревшая зависимость с известной CVE            |
| **Low**      | Пробел в харденинге / defense-in-depth                        | Нет security-заголовков, у cookie нет `SameSite`, нет audit-лога                                          |
| **Info**     | Полезно знать, само по себе не эксплуатируется                | Нет плана бэкапов, нет мониторинга, сгенерированный код, который стоит перечитать                         |

### 4. Отчёт

Используй ровно эту структуру:

```markdown
# Аудит безопасности — <имя репо> — <дата>

## Сводка

- Стек: <одна строка>
- Находки: <N critical, N high, N medium, N low, N info>
- Три вещи, которые чинить прямо сейчас: <буллеты>

## Находки

### [CRITICAL] <короткий заголовок>

- **Где:** `path/to/file.ts:42` (и другие локации)
- **Что:** <что делает код и почему это эксплуатируется>
- **Импакт:** <что получает атакующий>
- **Фикс:** <конкретное изменение, при необходимости с наброском кода>

### [HIGH] ...

(по одному блоку на находку, по убыванию severity)

## Проверено и ОК

<пункты чек-листа, которые проверены и безопасны — чтобы читатель видел охват>

## Не применимо

<пропущенные пункты с однострочной причиной>
```

Сортируй находки по severity, сверху самые тяжёлые. «Что» держи в несколько предложений на понятном языке — читателю не
должно приходиться реверсить находку. Для большого репо с множеством находок сохрани отчёт в Markdown-файл и покажи его,
а не вываливай всё инлайном.

## Заметки

- Предпочитай `rg` (ripgrep) вместо `grep -r` — он уважает `.gitignore` и быстрее. Если не установлен, откатывайся на
  `grep -rn`.
- **Проверяй git-историю, а не только рабочее дерево.** Секрет, удалённый из текущего кода, часто ещё живёт в
  `git log -p` / старых коммитах — это находка #13, и она встречается часто.
- Не полагайся на один сканер зависимостей. `npm audit` / `pip-audit` /
  `osv-scanner` ловят известные CVE, но полностью пропускают логические баги; самое интересное — в ручном чек-листе.
- Если чинишь, а не просто репортишь — перепроверь изменённый участок: фиксы иногда сдвигают баг (например,
  санитизировали вывод, но не второй sink).
