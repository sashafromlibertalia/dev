# /fullstack-feature — Сквозная разработка фичи

Ты ведёшь **одну фичу через два репозитория** так, чтобы API-контракт бекенда и фронта совпадали с первого раза. Это
главный анти-паттерн соло-фуллстека: изменил бек — забыл фронт (или наоборот) — поймал баг. Этот процесс не даёт
контракту разойтись.

## Механизм адаптации под проект

Архитектура унифицирована, но перед началом работы (на шаге 0) ты **обязан** проанализировать файловую структуру
проектов, `CLAUDE.md` (если есть), `tsconfig.json` (псевдонимы путей) и существующие модули.

- Если в проекте принят другой путь для фичей (например, не `features/`, а `modules/`), ты должен переключиться на него.
- Если на фронте используется специфичный стек (например, Vue, Svelte, Angular вместо React), ты адаптируешь шаг 5 под
  соответствующие паттерны этого фреймворка, сохраняя суть (API-слой, хуки/composables, компоненты).
- Пакетный менеджер: строго **pnpm** для обоих репозиториев.

## Два репозитория

Оба репо лежат в едином воркспейсе (например, `back/` и `front/`). Пути ниже — базовые, ты должен скорректировать их под
реальную структуру воркспейса в текущей сессии.

- **Бекенд** (ведущий): NestJS + TypeScript + pnpm + (Postgres/Prisma/TypeORM и т.д.). Фичи обычно лежат в
  `back/src/<domain>/` или `back/src/modules/<name>/`. У каждой фичи должен быть README.md. Индекс — в `back/docs/`
  (если принят в проекте).
- **Фронтенд**: TypeScript + pnpm. Домены/фичи обычно в `front/src/domains/<name>/` или `front/src/features/<name>/`.
  API-слой — `front/src/shared/api/` (или `services/`). Индекс — в `front/docs/` (если принят).

> Если репозитории подключены к сессии как раздельные рабочие директории, используй фактические пути из окружения
> сессии. Для точечной разведки без засорения контекста используй субагентов **frontend-scout** (с бека) /
> **backend-scout** (с фронта).

## Направление по умолчанию: С БЕКЕНДА

Ведущим в fullstack остаётся **бекенд**: контракт определяет сервер. Порядок: **контракт → бекенд → фронт → сверка**.
Если пользователь явно хочет начать с UI — предупреди, что контракт всё равно фиксируется на бекенде до реализации
фронта, и уточни форму ответа с ним.

## Процесс (7 шагов)

### 0. Понять фичу и определить scope

- Что за фича, какую задачу решает. Уточни неясное ПЕРЕД кодом.
- **Адаптация:** Изучи дерево файлов обоих репозиториев. Определи, где именно создаются новые сущности (как называются
  папки модулей/доменов на беке и фронте).
- Реши: это новый бекенд-модуль или расширение существующего? Новый домен на фронте или существующий?
- Найди аналоги в обоих репо для reference (как уже реализованы похожие эндпоинты и экраны).

### 1. Зафиксировать контракт (СНАЧАЛА, до кода)

Опиши в ответе явный контракт эндпоинта (ов) — это источник правды для обеих сторон. На беке он ляжет в basis
DTO-классы:

```
Эндпоинт: <METHOD> <path>
Auth: JWT / S2S / public / Guards
Request (body/query): <поля: тип, обязательность, валидация (например,.decorators NestJS)>
Response 200: <поля: тип, вложенность>
Ошибки: <коды HTTP и условия, Exception Filters>
Идемпотентность / лимиты: <если применимо, Throttler>
```

Для критичных фич (баланс/награды/платежи/статусы) сверься с Security Checklist проекта.

### 2. Спланировать обе стороны

Вызови агента **planner** (бекенд) для плана серверной части. Отдельно набросай план фронта (домен, страница,
хук/composable, типы). Явно перечисли:

- **Бекенд (NestJS):** Модуль, Controller, Service, DTOs (`*.dto.ts`), Entity/Schema, миграции (если нужны), регистрация
  в `AppModule` (или feature-flag модуля).
- **Фронтенд:** Домен, константа/метод в API-сервисе, типы request/response (рекомендуется импорт или дублирование
  строго по контракту), хук (query/mutation), ключи кэша, страница/компонент, i18n.

### 3. Реализовать БЕКЕНД (NestJS)

- Пиши по плану, используя паттерны NestJS (DI, Guards, Interceptors, Pipes).
- Создай строгие DTO с `class-validator` и `class-transformer` (или эквивалентными DTO из swagger), опираясь на контракт
  из шага 1.
- Для баланса/наград/транзакций — транзакции БД (например, через TypeORM/Prisma), идемпотентность, локи; вызови
  **tester** и `pnpm run test`, затем **code-reviewer**.
- Обнови README модуля (если принято в проекте).
- Проверь: `pnpm run build` (в директории бека), `pnpm run lint`.

### 4. Сверить фактический контракт

После реализации бека **проверь реальную форму ответа** (что именно возвращает Controller, как работают Interceptors,
например, обертка в `{ data: ... }` или прямой возврат) — она должна совпасть с шагом 1. Если контракт по ходу изменился
из-за NestJS-специфики — обнови описание из шага 1, это новая правда для фронта.

### 5. Реализовать ФРОНТ под известный контракт

- Добавь вызов эндпоинта в API-слой фронта, типы request/response — **точно по контракту шага 4**.
- Хук для получения данных (query) или мутации с правильным ключом кэша; инвалидация кэша после мутаций.
- Компонент/страница, формы (с валидацией, например, zod/yup), i18n.
- Для денег/действий: блокировка двойных кликов (disable кнопки при loading), обработка error/success, подтверждение
  опасных действий.
- Обнови README затронутой фичи (если принято в проекте).
- Проверь: `pnpm run build` (в директории фронта), `pnpm run lint`.

### 6. Финальная сверка и отчёт

- Пройди по контракту: каждый пункт request/response реализован с обеих сторон одинаково.
- Прогонит ли фронт реальный ответ бекенда без падений (особенно важно, так как оба на TS — проверь совпадение
  интерфейсов, optional поля `?`, вложенность)?
- Отчёт: что сделано на беке (модуль, эндпоинт, файлы), что на фронте (домен, экран, хук), обновлённые README, риски.

## Коммиты

Бек и фронт — **разные репозитории**, коммить раздельно. Предложи единое префиксное имя ветки в обоих (например
`feature/<feature-slug>`), чтобы связать их визуально. Коммить только по просьбе пользователя; на защищённой ветке —
сначала новая ветка.

## Чего НЕ делать

- ❌ НЕ писать фронтенд-типы до фиксации контракта — это источник рассинхрона.
- ❌ НЕ пропускать обновление README/документации обоих затронутых слоёв (если это стандарт проекта).
- ❌ НЕ пропускать тесты и ревью для критичных фич (деньги, статусы, безопасность).
- ❌ **КРИТИЧНО ДЛЯ TS:** НЕ путать файлы репозиториев. Оба репо на TypeScript, но у них разные `tsconfig.json`, разные
  алиасы (`@app/`, `@shared/` и т.д.) и разные `node_modules`. Строго проверяй, в каком дереве ты пишешь и откуда
  делаешь импорты.
