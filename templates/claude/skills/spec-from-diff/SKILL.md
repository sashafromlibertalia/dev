# /spec — ТЗ для разработчика на основе изменений

Ты превращаешь git-дифф в точное, action-oriented ТЗ для другого разработчика. Чаще всего фронт уже реализован (как в
этом проекте) и нужно, чтобы бекендер догнал контракт. Поэтому **источник правды — код диффа**, а не слова пользователя:
реальные типы, реальные пути эндпоинтов, реальные коды ошибок.

## Когда использовать

- Фронт уже реализован → нужно ТЗ бекендеру на реализацию контракта.
- Бекенд уже реализован → нужно ТЗ фронтендеру на интеграцию (меняется адресат и акценты, но процесс тот же).
- Любое «опиши изменения для X» / «сделай ТЗ по коммиту Y».

## Источники диффа

Если пользователь не указал явно — возьми **последний коммит** (`HEAD`). Иначе:

| Запрос пользователя                    | Команда                                                       |
|----------------------------------------|---------------------------------------------------------------|
| «по последнему коммиту» / «по дефолту» | `git show HEAD`                                               |
| «по коммиту abc123»                    | `git show abc123`                                             |
| «по staging» / «по индексу»            | `git diff --cached`                                           |
| «по рабочим изменениям»                | `git diff`                                                    |
| «ветка vs main»                        | `git diff main...HEAD`                                        |
| «по файлу/папке X»                     | `git log -p -- X` (или `git diff` если нужны незакоммиченные) |

Полезно сразу получить: `git show <ref> --stat` (обзор) + полный `git show <ref>` (детали).

## Процесс (6 шагов)

### 1. Собери дифф и определи scope

- Выбери источник диффа (см. таблицу выше).
- Прочитай `--stat` — какие домены/слои затронуты (api, shared/api, features, widgets, i18n).
- Если есть cherry-pick-метка в коммите — раскрой исходный коммит тоже (`git show <orig>`), бывает что смысл в нём.

### 2. Извлеки контракт из кода (это ядро ТЗ)

Прочитай **фактические** изменения, не догадывайся. Что искать:

| Артефакт в коде  | Где обычно лежит                                                 | Что извлечь                                  |
|------------------|------------------------------------------------------------------|----------------------------------------------|
| Эндпоинты        | `src/domains/<domain>/api.ts`                                    | METHOD, path, тело запроса, тип ответа       |
| Типы запроса     | `src/shared/api/requests.ts`                                     | поля, обязательность, инварианты             |
| Типы ответа      | `src/shared/api/responses.ts`                                     | поля, вложенность, что убрано/добавлено      |
| Валидация        | `features/<x>/schema.ts`, `entities/.../operations.ts` (valibot) | правила, сообщения, edge-cases               |
| Обработка ошибок | формы (`catch`, `ApiError.status`)                               | коды → пользовательские сообщения            |
| Бизнес-семантика | комментарии, i18n-хинты (`*-hint`, `*-description`)              | что значит каждое поле «человеческим» языком |
| Мутации и кэш    | `src/domains/<domain>/shared/api/index.ts`                       | что инвалидировать, оптимистичность          |

Если в диффе меняются типы в `shared/api/*` — это **контрактный** change, его подсвети отдельно.

### 3. Определи адресата и направление

- По умолчанию для этого репо: **бекендер** (Go, `internal/features/clubhost`).
- Если пользователь явно просит «для фронта» / «для мобилки» — поменяй адресата и реципиента контракта.
- В случае reverse-направления (бек сделан, нужно ТЗ фронту) — акценты смещаются: меньше валидации, больше «куда
  положить типы / хуки / страницы / i18n по конвенциям проекта».

### 4. Собери ТЗ по шаблону (ниже)

Подставь извлечённое в секции. Каждое утверждение должно быть **проверяемым** — либо ссылка на код (`file:line`), либо
явное правило. Никаких «должно работать стабильно».

### 5. Сохрани ТЗ файлом (по умолчанию)

ТЗ — это документ, с которым потом работает другой разработчик, поэтому **основной результат — файл на диске**, а не
дамп в чат.

- Путь по умолчанию: `docs/<адресат>-spec-<слаг>.md` — например `docs/backend-spec-limit-operations.md`,
  `docs/frontend-spec-club-settings.md`. Адресат из шага 3, слаг — kebab-case, отражает суть фичи (не `spec1.md`).
- Если пользователь указал свой путь/имя — используй его.
- Если каталога `docs/` (или указанного) нет — создай (`mkdir -p`).
- Если файл с таким именем уже есть — не перезатирай молча: добавь короткий суффикс (`-v2`) или спроси, если
  расхождение существенное.
- Запиши файл, затем **выведи в чат**: путь к файлу + секцию «Открытые вопросы» (по ней пользователю нужно
  действовать сразу). Полный текст ТЗ в чат не дублируй — он уже в файле.

Если пользователь явно просит «не сохраняй» / «просто в чат» — тогда отдай ТЗ в чат и файл не создавай.

### 6. Отчитайся

Одной строкой: что за фича, куда сохранил, сколько эндпоинтов/полей затронуто, есть ли breaking changes. Затем —
«Открытые вопросы», если они есть.

## Шаблон ТЗ

```markdown
# ТЗ: <суть фичи> — <адресат: backend | frontend | mobile>

**Контекст:** <что уже сделано в этом репо, какой коммит/ветка — источник правды>
**Цель:** <одно предложение — чего должен достичь адресат>
**Аудитория:** <роль и стек: «Бэкенд-разработчик, Go, internal/features/<x>»>

---

## 1. Контракт API

По каждому эндпоинту (новому/изменённому): METHOD + path, тело запроса с jsonc-примером, ответ 200, таблица кодов ошибок
с условиями. Для breaking change — отдельный callout (⚠️).

## 2. Валидация (server-side)

Таблица: поле → правило → текст сообщения. Это то, что фронт уже проверяет через valibot — бек обязан проверять то же
самое. Особое внимание sentinel-значениям (например -1 = «безлимит», 0 — невалидно).

## 3. Модель данных

Актуальный TypeScript-shape, которого ждёт фронт (`file:line`). Что добавилось, что убралось.

## 4. Хранение и миграция

Если меняется схема/модель — где хранить, дефолты для существующих записей, инварианты (NOT NULL и т.п.).

## 5. Интеграции / бизнес-семантика

Оркестраторы, фоновые процессы, побочные эффекты. Таблица i18n-ключей с человекочитаемыми текстами — это лучшая
документация семантики полей.

## 6. Приёмка

Чек-лист (`- [ ]`) — конкретные проверяемые шаги: «POST /x делает Y», «ошибка Z → 4xx», «миграция проставила дефолты».

## 7. Открытые вопросы

Что требует уточнения от пользователя/команды (единицы времени, форма ответа, кросс-проверки).

---
**Ссылки на эталон:** `file:line` на ключевые точки фронтенд-реализации.
```

## Конвенции проекта (где что искать)

- Эндпоинты и тела запросов — `src/domains/<domain>/api.ts`, вызывают `ApiClient.request<T>(path, { method, body })`.
- Контрактные типы — `src/shared/api/requests.ts` (тела) и `src/shared/api/responses.ts` (ответы).
- HTTP-стек — `ky` в `ApiClient` (`src/shared/api/client.ts`); 401 → refresh + 1 retry; ошибки — `ApiError` с `.status`.
- Валидация форм — valibot, схемы в `features/<x>/schema.ts` и общих модулях вроде `entities/<x>/operations.ts`.
- Серверное состояние — react-query, мутации в `src/domains/<domain>/shared/api/index.ts`, инвалидация по query-key
  фабрикам из `src/shared/api/query-keys.ts`.
- Тексты и хинты (семантика полей!) — `_.i18n/en.js` и `_.i18n/ru.js` рядом с фичей.
- Бекенд-адресат: Go, домены в `internal/features/clubhost/` и т.п.

## Правила качества (self-check перед ответом)

- [ ] Каждое поле в ТЗ имеет тип и правило — никаких «какие-то опциональные поля».
- [ ] Каждый эндпоинт — METHOD, path, тело, ответ, коды ошибок.
- [ ] Валидация бека повторяет valibot-схему фронта (иначе контракт разъедется).
- [ ] Sentinel-значения описаны явно (`-1` = безлимит, и т.п.) — это частый источник багов.
- [ ] Breaking changes подсвечены (убранные/переименованные поля, изменившиеся коды ответа).
- [ ] В каждой секции есть хотя бы одна ссылка `file:line` на источник правды.
- [ ] Приёмка — чек-лист конкретных шагов, а не «работает корректно».
- [ ] Открытые вопросы вынесены отдельно, не спрятаны в текст.
- [ ] Файл сохранён в `docs/` (или по указанному пути), путь выведен в чат.

## Чего НЕ делать

- ❌ Не выдумывать пути эндпоинтов/имена полей — только из кода. Если не нашёл — так и скажи в «Открытых вопросах».
- ❌ Не пересказывать дифф построчно — ТЗ читает разработчик, которому нужна **суть и контракт**, не лекция.
- ❌ Не вставлять «надёжное», «масштабируемое», «стабильное» — это мусор.
- ❌ Не дублировать полный текст ТЗ в чат после сохранения — в чат идут только путь и открытые вопросы.
- ❌ Не перезатирать существующий файл молча.
- ❌ Не пропускать секцию «Приёмка» — без неё ТЗ нельзя сдать.
